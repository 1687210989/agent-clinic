- 修订日期：2026-10-15
- 修订依据：**《agent-clinic 独立评估报告（实测版）》**（第三方，下载 Node 22.20.0 + 合成 DSH 语料实跑 6 组测试）
- 修订性质：**不改变项目定位与诊断层设计**，只针对评估暴露的质量保障层缺陷与判定健壮性缺陷做调整

## 0. 修订摘要

评估报告的总评：诊断准确性 **A-**、证据可复核性 **A**、自检可信度 **C+**、环境可移植性 **C**、判定健壮性 **B**、工程纪律 **B+**。

也就是说，**风险不在诊断层，在质量保障层**：诊断核心链路（扫描 → 判定 → 证据 → 报告）经第三方实测零误报零漏报、数字分毫不差；但 CI 全红未修、徽章 249/249 与实测 247/2/退出码 1 不符、自检依赖作者本机数据形态。一个把「每条结论都可复核」写进产品理念的工具，它自己的绿灯不可复核 —— 这是本次修订要消除的首要问题。

本次修订四条主线（严格对应评估报告 §三/§四/§八）：

1. **把绿灯变真**：修 smoke 降级语义 + CI 造合成会话 + 徽章由机器校验（对应 §3.1、§3.2、§4.2）
2. **处方层数据流贯通**：名额轮转修复 + 现搜条目端到端进处方（对应 §4.1）
3. **判定健壮化**：N3 outcome 三分类、C1 基线排除自身（对应 §4.3、§5.1）
4. **发布门槛前置**：以上全绿才谈上线与收录（对应 §八）

## 1. 项目定位与边界（保持不变）

**定位**：只读扫描 DSH 本地会话，用可复核证据诊断 Agent 使用问题，并开出可执行处方。

| 维度 | 约定 | 本次是否变更 |
|---|---|---|
| 数据来源 | 仅本地 DSH 会话目录（`~/.dsh/sessions`），默认零外发 | 不变 |
| 写权限 | 全流程不写会话文件（评估报告 §六.3 实测确认） | 不变 |
| 无数据行为 | 优雅降级，逐维度说明"为什么没有数据"（§六.4 实测确认） | 不变（但**退出码语义要改**，见 4.2） |
| 口径 | 实测 vs 估算分开标注（§六.5 实测确认） | 不变 |
| 依赖 | 零第三方运行依赖、离线可用（§六.7 实测确认） | 不变 |
| 差异化核心 | 证据可复核（report 给出的定位符与 show 展开严格一致，§六.2） | 不变，且新增护栏守护 |

评估报告证实成立的内容**一律保留**：10 项指标判定逻辑、证据层、只读承诺、降级说明文案、口径标注、零依赖离线运行、三旋钮（maxSessions / minRepeatCount / contextLines）、插件目录三来源。

## 2. 指标体系与判定健壮性（修订）

指标总数与类别不变：**19 项**（C1 C2 C3 C5 C6 C7 · E1–E5 · N1–N4 · A2 A3 A4 A5），A1(MCP) 排期，K1/K2 因隐私取舍不实现。

### 2.1 N3「被拒」判定：由二分类改为三分类

**现状（缺陷）**：`src/diagnostics/index.mjs:831`

```js
if (!/^allow/i.test(outcome)) denied += 1;
```

任何非 `allow*` 开头的 outcome 都被计为"拒绝"。评估报告实测：5 个 `approved` 被报成"被拒 5 次"；若 DSH 改用 `approved` 措辞，所有 N3 报告的"被拒"字段将系统性全错，而用户会据此调整权限配置。

**调整后**：显式匹配拒绝语义，其余归入"未知结果"，绝不猜。

```js
const outcome = String(d.outcome ?? '').toLowerCase();
if (/^(deny|denied|reject|rejected|decline|declined|refus|forbid)/.test(outcome)) denied += 1;
else if (!/^(allow|approv|accept|grant|ok|yes|permit)/.test(outcome)) unknownOutcome += 1;
```

- 分母口径同时写清：`审批请求 N 次 · 被拒 X 次 · 未知结果 Y 次 · 无决定记录 Z 次`（`unknown` 现有语义保留为"无对应决定记录"，与"未知结果"分列）
- 报告文案不再把非 allow 一律说成拒绝
- 文档：`docs/diagnostics.md` 的 N3 条目同步改写（该文件是"指标 = 代码镜像"，含断言）

### 2.2 C1 基线排除被判定者自身

**现状（缺陷）**：`src/diagnostics/index.mjs:442`

```js
const baselinePool = stats.filter((x) => !x.subagent && x.output > 0).map((x) => x.perRequest);
const base = median(baselinePool);
```

基线池含被判会话自己，评估报告 §5.1 指出（中位数对离群值稳健，本次结果仍对，但严格实现应排除自身）。

**调整后**：逐会话计算排除自身后的基线。

```js
const poolEntries = stats.filter((x) => !x.subagent && x.output > 0);
// 逐个会话排除自身后再取中位数：自己不该是自己的对照
```

**必须同步的连带影响（口径更正：本方案 v0.2 初稿此处写反了，现更正）**：排除自身后基线**更低** → 倍率**更高** → 判定**更敏感**，而不是"更宽松、降低误报"。以评估报告 §5.1 的例子 `[100, 250, 2000]`（每会话 200 条 assistant 事件，perRequest = 单位请求 output）为例：

| 口径 | 中位数基线 | 2000 的倍率 | C1 是否命中 |
|---|---|---|---|
| 旧：含自身 | 250 | 8.0× | 命中 |
| 新：不含自身 | 175 = median(100, 250) | 11.4× | 命中（阈值 2 倍） |

即该修正会让**历史报告里的倍率整体变大**，可能让原本刚好低于阈值的会话转为命中（宁可多报，不少报）。

处理方式：
- `docs/diagnostics.md` 明确写"基线 = 排除被判会话后的其余主会话中位单位请求 output（对照样本不足时退回全体主会话并在摘要标注）"
- `CHANGELOG.md` 标注"判定口径变更：C1 基线排除自身，历史报告倍率可能上升"
- smoke 新增护栏断言：3 会话 `[100, 250, 2000]` 下摘要必须含 `是主会话基线 175 的 11.4 倍` 且 C1 命中（防回退到含自身口径，也防有人以为这会让误报变少）

## 3. 处方层数据流（修订重点）

### 3.1 名额轮转修复：第 2 个名额此前永远发不出去

**实测复现（本项目自查，非评估报告原文，但正是 §4.1 现象的成因）**：

```
$ node .tmp/repro-live-rx.mjs
C1 单点处方: config:<default-model> | plugin:demo-ctx-compress | behavior:behavior-split-session
全局处方( 7 类问题): config … | command … | behavior … | config … | config … | behavior …
现搜条目在全局处方里吗: false
```

**根因**：`src/prescriber/index.mjs:520-548`，`matchPrescriptions` 的轮转被"第 0 轮吃光名额"破坏：

```js
for (let round = 0; round < Math.max(perFinding, 1) && out.length < limit; round++) {
  for (const f of findings) { if (out.length >= limit) break; … pick = all[round] … }
}
```

`perFinding=2`、`limit=6`：当 finding 类数 ≥ 6 时，第 0 轮就把 6 个名额填满，`round=1` 永不执行 —— **每类问题的第 2 个名额（插件类处方所处位次）结构性丢失**。

**调整后**：给每一轮保留配额，保证后续轮次一定有位置。

```js
// 每轮配额 = 总名额 / 轮数（上取整），避免第 0 轮吃光全部名额：
// perFinding=2、limit=6 时每轮 3 个 —— 第 1 轮必定执行，插件类处方才有机会进入全局列表。
const roundCap = Math.max(1, Math.ceil(limit / Math.max(perFinding, 1)));
```

未入选的候选不静默丢弃：报告与面板对"因名额未展示"的处方给出计数（沿用既有"不静默降级"原则）。

### 3.2 现搜条目端到端进处方（评估 §4.1）

评估报告的最小复现：注入结构合规的现搜条目 `demo-ctx-compress`（能力标签对上 C 类）后，`live 进推荐了吗: true`，但 `插件类处方: [ '@shengsheng/dsh-taskboard' ]` —— 现搜只进推荐、不进处方，用户点完"联网现搜"看不到期望结果。

**修正后的准确描述**（本项目复核）：现搜条目**已经能进入 C1 的单点/聚合卡处方**（`src/report.mjs:311`、`src/report.mjs:328` 走的是 `prescribeOne`），但进不了全局 `prescriptions` 列表（`src/report.mjs:297` → `matchPrescriptions`）。也就是说：

- 属实缺陷：受 3.1 的名额轮转 bug 影响，全局处方段（报告末尾"处方"清单、CLI 输出）里现搜条目缺位
- 断言缺陷：`scripts/smoke.mjs:1511-1515` 断言的正是全局列表，于是**该断言能否通过取决于本机扫描出几个 finding 类**（类数 < 6 时通过，≥ 6 时必然失败）—— 与 §4.2 同属"自检不自包含"

**调整后（两条一起改）**：

1. 实现侧：3.1 的轮转修复，保证 ≥6 类问题时插件类处方仍能获得名额
2. 断言侧：改为**不依赖本机数据形态**的双重断言
   - 针对性断言：构造 finding 集与现搜条目，断言 `prescribeOne(C1 finding, { ctx })` 结果里含该条目（per-finding 口径）
   - 名额护栏断言：构造 7 类 finding + 1 条现搜条目，断言其出现在 `matchPrescriptions(..., { ctx })` 输出中（防 3.1 回退）
   - 现有"全局列表含该条目"的断言保留，但输入改为上述构造数据，不再读本机 `scan`

## 4. 质量保障体系（重写）

评估报告的核心批评：**「249/249」当前只能靠作者自觉**。本节把绿灯变成机器可验证的。

### 4.1 自检语料固定装置：`scripts/fixtures/synth-dsh.mjs`（新增）

评估报告 §4.2 指出：「合并确实压掉了重复（类数 < 处数）」要求每个指标命中 ≥2 处，干净合成数据（每指标 1 处）下必挂 —— **248 项自检是针对作者本机数据校准的，不是自包含的**。

**调整后**：把评估报告测试 3/测试 4 用到的合成语料固化为仓库内生成器，并写死不变式：

- 输出一个完整可用的合成 `DSH_HOME`（`--out <dir>`），多帧 zstd（覆盖 `src/adapters/zstd-frames.mjs` 的按 magic 切帧路径）
- 覆盖 13 种以上 DSH 事件类型：正常对话、死循环、冗余调用、大结果、审批（含 `approved` / `deny` / 未知 outcome 三类）、压缩（`shadowedTokenCount`）、注入（`request/header`）、大 tool schema、高消耗、skill 触发（**必须走 skill 工具 + `arguments.name`**，A2 才不会误报）
- **不变式一：每个指标至少命中 2 处**（尽力而为 —— 原意是"合并类断言要有得比"，但第三方评估 §4.2 之后那些断言已改为**构造输入**，≥2 不再是正确性前提）
- **不变式二：每个指标至少命中 1 处**（硬门槛：保证各诊断分支都被触达，命中 0 即非零退出）
- 生成器自带自校验：跑一遍诊断，逐指标打印命中处数（`--verify`）；不足 1 处直接 exit 1
- 生成器为唯一语料来源：CI 与本地"无数据环境复现"都指向它（评估报告测试 1/测试 3 的语料与生成脚本可直接复用）
- **实施期新增（方案初稿未预见）**：A2「skill 闲置」的一半输入是"这台机器装了哪些 skill"（`src/diagnostics/index.mjs:1243` 的 `listInstalledSkills()` 读 `$HOME/.agents/skills`、`$HOME/.workbuddy/skills`，与 `DSH_HOME` 无关）—— 全新的 CI runner 上必然 0 个已装 skill → A2 命中 0 → 语料自检假红，正是 §4.2 那类"断言绑在宿主机上"的病。**修法**：新增 `AGENT_CLINIC_SKILL_DIRS`（路径分隔符分隔，未设时行为不变），语料自带一个必然闲置的 demo skill 目录，CI 与 `--verify` 都指向它；smoke 增一条断言守住该覆盖（`A2：已装 skill 名单可由 AGENT_CLINIC_SKILL_DIRS 给定`）
- **实施期实测命中数（`--verify` 实跑）**：C1/C2/C3/C5/C6/E1/E2/E3/E4/E5/N1/A3 = 2，C7/N2/N3/N4/A2/A4/A5 = 1 → 19/19 命中，`DSH_SMOKE_REQUIRE_DATA=1` 下 smoke 263 通过 · 0 失败 · 0 跳过

### 4.2 smoke 降级语义：skip ≠ fail

**现状（缺陷）**：`scripts/smoke.mjs:62` `check('会话根目录存在', fs.existsSync(root), root)` 与 `:65` 在无数据环境计为失败，`:68-71` 虽打印"无会话数据，跳过剩余检查"，但**跳过前的断言已计为失败**，降级逻辑形同虚设 → `:2273 process.exit(fail === 0 ? 0 : 1)` 退出码 1。这正是 CI 全红的根因。

**调整后**：

- 新增 `skipCheck(name, reason)`：不计入 `fail`、不计入 `pass`，单独计数 `skip`，输出 `⊘ name —— reason`
- `:62`/`:65` 改为：无会话根目录 / 扫不到文件时走 `skipCheck`，其余检查照旧跳过
- 新增环境变量 `DSH_SMOKE_REQUIRE_DATA=1`：设置后 **skip 直接升级为 fail**（CI 必设）。这样"无数据静默通过"在 CI 里不可能发生
- 汇总行改为 `通过 N · 失败 M · 跳过 K`，末尾第 18 段新增断言：`DSH_SMOKE_REQUIRE_DATA=1 时跳过数必须为 0`
- 退出码语义：`fail > 0 → 1`；`REQUIRE_DATA=1 且 skip > 0 → 1`；纯降级（无数据、未要求数据）→ 0，并在输出中写明"本次为降级运行，未验证的维度：…"

### 4.3 CI 重写（`.github/workflows/ci.yml`）

**现状（缺陷）**：`ci.yml:32-33` 的 smoke 步骤未设 `DSH_HOME`、未造合成数据 —— runner 上不存在 `~/.dsh/sessions`，退出码必为 1；两次 CI 运行 `conclusion: failure`，**当前所有提交都未经自动化验证**。

**调整后步骤序列**：

```yaml
- name: 生成合成会话语料
  run: node scripts/fixtures/synth-dsh.mjs --out "${{ runner.temp }}/dsh-home"
  env: { DSH_HOME: "${{ runner.temp }}/dsh-home" }

- name: 自检（合成数据，3 平台 × node 22.15/24）
  run: node scripts/smoke.mjs
  env:
    DSH_HOME: "${{ runner.temp }}/dsh-home"
    DSH_SMOKE_REQUIRE_DATA: '1'

- name: 自检（空数据降级，必须退出码 0）
  run: node scripts/smoke.mjs
  env: { DSH_HOME: "${{ runner.temp }}/agent-clinic-empty-home" }

- name: 徽章与实际通过数一致
  run: node scripts/badge.mjs --check

- name: 空数据下跑一次报告      # 保留
- name: 目录命令自检（不联网）  # 保留
```

- `privacy` job 保留不变（它守的是"仓库里不得出现会话数据/本地路径"，与本次修订无关）
- CI 状态徽章进入 README 顶部（见 4.4）

### 4.4 徽章治理（评估 §3.2：项目自身价值主张被直接违背）

**现状（缺陷）**：`README.md:21` 静态徽章 `smoke-249%2F249-brightgreen`；`README.md:110`、`README.md:344` 同样声称 249。实测 247 通过 / 2 失败 / 退出码 1。项目自检第 18 段（`scripts/smoke.mjs:2257`）断言了"声明的断言全部真的执行过"，**但没有断言守护徽章数字本身** —— 评估报告点名这是发布纪律缺陷。

**调整后**：

1. 新增 `scripts/badge.mjs`：
   - `--check`：跑 smoke（或读 `--from-file <log>`，规避宿主沙箱内 pipe 捕获 EPERM），解析汇总行 `通过 N · 失败 M`，对比 `README.md` 徽章数字与两处文字声称；不一致 → 非零退出并打印期望/实际
   - `--write`：本地维护者用，把徽章与文字改为实际值（**只在 CI 全绿后使用**）
2. README 徽章改造：
   - 静态数字徽章替换为 **CI 实际状态徽章**（GitHub Actions 工作流徽章）
   - `smoke N/N` 徽章保留，但由 `--write` 生成，并由 `--check` 在 CI 守护
   - `README.md:110`、`README.md:344` 的"249 项/249/249"改为由 `--write` 同步的数字
3. 新增自检断言（照抄项目已有的"声明的断言全部真的执行过"同款写法）：**README 声称的通过数 == smoke 实际通过数**，作为第 18 段第 3 条

**实施偏差（已落地，与初稿不同，必须如实记录）**：

- **没有新建 `scripts/badge.mjs`**，核对逻辑**内建进 `scripts/smoke.mjs` 的收尾段**：
  ①最终条数只有跑完才知道，独立脚本要么重跑一遍 smoke、要么解析日志，两者都更脆；
  ②沙箱内 `spawn` 捕获子进程输出会 EPERM（本项目踩过），"跑 smoke 再解析汇总行"这条路在受限期跑不通。
  因此 `--write-badge` 改为 smoke 自己的开关（仅 `fail===0 且 skip===0` 时才改写）。
- **守护范围比初稿多一个文件**：除 `README.md` 的三处（徽章、`冒烟测试 N/N 通过`、`自检（N 项）`）外，
  还核对 `SKILL.md` 的 `自检（N 项）` —— 它当时停在 233 项，是同一类漂移。
- **徽章策略**：静态 `smoke N/N` 徽章保留（由 `--write-badge` 同步 + 收尾段守护），
  另外新增一枚 **GitHub Actions CI 实况徽章**（就是工作流的真状态，改不了），
  两者并列并加一行说明，读者不必猜哪个可信。

### 4.5 断言自包含规则（硬约定，写入 CONTRIBUTING 段与 SKILL.md）

评估报告 §4.2 的教训固化为规则，防止同类缺陷再犯：

1. **禁止**断言依赖"本机恰好有对应数据"或"每指标恰好命中 N 处"；需要数据形态时用 `scripts/fixtures/synth-dsh.mjs` 或就地构造 scan 对象
2. **禁止**条件分支静默吞掉断言（沿用第 18 段既有机制，新断言一律无条件执行）
3. 新增/修改指标时，必须同步：`docs/diagnostics.md` 镜像条目 + 一条护栏断言 + 合成语料覆盖
