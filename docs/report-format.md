# 体检报告输出格式

> 供 SKILL.md 与 `cli.mjs report` 使用。全部输出**中文**，风格紧凑。

---

## 模板

```markdown
## Agent 体检报告（平台：DSH · 近 30 天 · N 个会话）

扫描概览：N 会话 / N 行 / N 次工具调用 / 错误率 X%
token：input N · output N · cacheRead N

### 发现 K 个问题（按严重度排序）

**[高] E1 死循环** —— 会话 <id>，<tool> 同参数重复 N 次
- 证据定位：<file>#L<start>-L<end>
- 复核命令：node src/cli.mjs show "<file>#L<start>-L<end>"
- 影响估算：约 N 次无效调用
- 置信度：高
- 处方：改配置·让重复调用提醒来得更早
- 已否决：调低默认推理强度 —— reasoningEffort 已经是 low（最低档）

### 未检测到异常的维度
E2 反复失败（错误率 7.3%，低于 30% 阈值）、C1、C2、A1、A2……

### 处方（N 条 · 每条都有可执行动作）

> 配置类处方改的是这份文件（本工具只读它，不代你改）：`~/.dsh/profiles/<p>/cordis.patch.yml`

1. **【改配置】收紧工具结果的 spill 预算** —— 针对 C2
   - 具体怎么做：
     1. 用任意文本编辑器打开这个文件：~/.dsh/profiles/desktop/cordis.patch.yml
     2. 在文件里搜索这一行：- id: spill-policy
     3. 分两种情况：① 搜到了 → 用下面的 YAML 片段整段替换（整体替换语义，没变的键也要写进去）；② 没搜到 → 追加到文件末尾
     4. 保存文件。profile 配置默认会热重载；若行为没变化，完全退出 Harness 再打开
     5. 验证：重跑 ./run.sh report，看 C2 的末轮 input 是否回落
   - 说明：超过预算的工具结果落到磁盘… 
     当前：maxInlineTokens=12500（随附默认值（你的 profile 未覆盖这一行））
     建议：maxInlineTokens=6000
   - 改成（可整段粘进 profile patch）：
     ```yaml
     - id: spill-policy
       name: '@deepseek-ai/dsh-spill-policy'
       config:
         maxInlineTokens: 6000
     ```
   - 依据：…
   - 风险提示：…
   - 怎么确认有效：…
   - 出处：@deepseek-ai/dsh-spill-policy（随附插件）· 核实于 2026-10-15

### 省 token 开关清单（本机真实存在，供按需调整）
> 这是**工具陈列**，不是体检结论 —— 本次未触发对应指标……
- **【装插件】装 Smart Compaction（模型择机压缩 + 用量可见）** …
  - 具体怎么做：1. 侧边栏 → 插件 → 添加插件 2. 粘贴 smart-compaction …

### 插件目录检索（目录 N 条 · 本地已装 M 个）
> 按「能力标签 + 关键词」从已核实的插件目录里检索出来的相关插件 —— 每条都说明**为什么命中**。
**针对 C1**
- **Billion Context（ACP 上下文压缩）**（`billion-context-dsh`，未安装）
  - 能力：context-compaction / long-session / token-saving
  - 命中原因：能力标签「token-saving」对上 C1 需要的能力；你的问题描述里出现了「token」「消耗」
  - 安装：侧边栏 → 插件 → 添加插件 → 粘贴 billion-context-dsh
  - 核实：2026-10-15 · https://github.com/Tyan66666/billion-context-dsh

### 未实现（骨架阶段）
A1
```

## 硬性要求

| # | 要求 |
|---|---|
| 1 | 每个结论必须带 **证据定位** 与 **复核命令** |
| 2 | 处方默认 **≤4 条**，每个问题 **≥1 条**；每条必须给出可执行动作（YAML 片段 / 命令 / 插件入口 / 界面路径 / 指向具体动作的建议）+ **分步操作指引** + 风险 + 验证方式 + 出处 |
| 3 | 配置类处方必须写明 **当前值 → 建议值** 与配置文件路径；当前值已不弱于建议时**撤掉该条**并写明"已否决"原因 |
| 4 | **必须**列出"未检测到异常的维度" —— 禁止只报问题不报正常 |
| 5 | 必须列出"未实现的维度" —— 让用户知道覆盖面，不假装全知 |
| 6 | 插件推荐必须来自**已核实的插件目录**，且每条都要给出**命中原因**（能力标签 / 关键词），不做黑盒推荐；已安装的不推"安装" |
| 7 | 软信号（K2）措辞必须含"疑似"，且不得为"高"严重度 |
| 8 | 零对话原文；证据片段默认截断 400 字符 |
| 9 | 结尾注明数据完整性问题（坏帧 / 坏行 / 解析失败），如有 |

---

## 语气

- 直接，不客套
- 不确定就说不确定
- 不夸大影响（"约 1.8 万 token" 而非 "浪费了海量 token"）
- 没有问题时，明确说"未检测到异常"，而不是硬凑一条
